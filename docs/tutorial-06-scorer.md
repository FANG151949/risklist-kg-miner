# 教程 06：v0.6 风险分级 scorer + 人工复核队列

## 需求（谁提的、原来怎么痛）

v0.5 交付后业务方的反馈很典型：

1. "名单太长了。审批岗同事一天看不了几十个人，**谁优先盯**？"
2. "图里挂 `[conflict]` 的那个陈志远，状态一直悬着，**谁来收这个尾**？"

原来的做法：全量名单平铺给人工，重要的和不重要的一起排队；
冲突状态没人认领，最后不了了之。

**验收标准**：每条合并结论有可解释的风险等级与建议；状态未定的一律
进入人工复核队列，不占名单、不下结论。

## 核心设计：评分卡（rule-first 的名单版）

风控域的经典做法——每个风险信号一个**分值和一个理由**，加总出分，
查表定级。零 LLM、可解释、可单测，业务方要挑战结果时能把每一分
拆给他看（demo 输出里 `conflict(40) + removed(25) + no_date(10)` 就是拆分）。

| 信号 | 分值 | 理由 |
|---|---|---|
| conflict（状态跨公告冲突） | 40 | 状态未定，不能下结论 |
| removed（存在免职记录） | 25 | 离任关注信号（名单挖掘场景） |
| no_date（生效日期缺失） | 10 | 信息质量低 |
| single_source（单源） | 10 | 未经交叉验证 |

等级：≥40 高 / ≥20 中 / 其余低。建议优先级：**conflict → 转人工复核**
（压过一切分数逻辑）> 高 → 纳入重点名单 > 中 → 持续观察 > 低 → 常规。

注意 40 分的量纲设计：conflict 单独一项就到"高"级门槛——冲突的人
不管别的信号如何，永远是最需要处理的一档。

## 步骤 1：跑 demo

```bash
uv run python -m risklist_kg_miner.scorer
```

预期输出（真实语料 14 条记录 → 11 组结论）：

```
== 风险分级（评分卡可解释） ==
  [高] 75分  陈志远 @河州市发展和改革委员会副主任  <- conflict(40) + removed(25) + no_date(10)  建议: 转人工复核
  [高] 45分  吴国强 @市公路管理局局长  <- removed(25) + no_date(10) + single_source(10)  建议: 纳入重点名单
  [高] 45分  冯建华 @市水利局局长  <- removed(25) + no_date(10) + single_source(10)  建议: 纳入重点名单
  [中] 35分  王建国 @河州市财政局局长  <- removed(25) + single_source(10)  建议: 持续观察
  [中] 25分  孙丽华 @河州市卫生健康委员会副调研员  <- removed(25)  建议: 持续观察
  [低] 10分  林慧敏 / 赵天宇 / 罗建军 / 唐雪 / 郑海涛  <- single_source(10)  建议: 常规
  [低]  0分  周晓梅  <- 无信号  建议: 常规

== 人工复核队列（conflict 强制进队，共 1 条） ==
  陈志远 副主任 @河州市发展和改革委员会  来源冲突: notice-001 vs notice-006  分数 75
```

两个业务看点：

1. **高风险 ≠ 冲突**：吴国强、冯建华没有冲突，但"免职+单源+无日期"
   三信号叠加同样到 45 分进重点名单——评分卡捕捉的是信息本身的
   风险特征，不只是校验层的状态；
2. **队列只收 conflict**：吴国强虽是高风险但**状态明确**（就是被免了），
   不占人工复核资源——复核队列是稀缺的人工工时，只留给"机器定不了"
   的事。这是"宁可漏报不误报"与运营效率的平衡点。

## 步骤 2：代码与测试（src/risklist_kg_miner/scorer.py）

- `SIGNALS` 信号表：分值与理由集中定义，调分值只改一处（但**改了要同步
  改测试**——测试钉的是业务承诺，不是实现细节）；
- `score()`：MergeResult -> RiskAssessment，纯函数；
- `review_queue()`：只收 conflict 项。docstring 里留了扩展位：
  **复核结论回流**（人工确认后回写 STAFF status 并沉淀为后续合并的
  先例知识）——这是全项目唯一设计好的"跨会话记忆"接口，对应公司
  项目无持久记忆的现状，作为我们的差异化扩展。

tests/test_scorer.py 钉死的承诺：

| 测试 | 承诺 |
|---|---|
| test_conflict_is_high_risk_and_queued | conflict+免去+无日期 = 75 分高险，进队列 |
| test_conflict_overrides_score_for_queue | 有日期的 conflict 仍必进队列 |
| test_removal_single_source_no_date_is_high | 三信号叠加 45 分高险，但**不进队列**（状态明确） |
| test_multi_source_appointment_is_low | 干净任命 0 分常规 |
| test_real_samples_only_chen_conflicted_goes_to_queue | 全量语料只有陈志远进队列，11 组结论 |

## 面试 hook

- "风险分级怎么做的？" → 评分卡：信号/分值/理由集中定义，可解释可单测，
  LLM 只在校验层兜底语义冲突，评分层完全确定性——风控系统的审计要求。
- "conflict 为什么不看分数直接进队列？" → 复核工时稀缺，队列语义是
  "机器定不了"，不是"分数高"；宁可漏报不误报的落地。
- "和公司平台的评分有什么不同？" → 公司平台规则打分面向配置合规；
  这里信号面向人事名单业务，但方法论同源：确定性规则优先。
