# 教程八（v0.8）：精排 rerank + 流水线封装 + CLI

> 上一版结尾留了两个活口：① v0.7 消融显示 precision@8 仅 ~18%（top-8 六成是噪声），
> rerank 列入 v0.8；② 整个系统是五个散装模块，要按教程顺序手跑——演示可以，
> "每天来几篇新公告"的真实使用方式不存在。这一版把两个都收掉。

## 需求（谁提的、原来怎么痛）

- **检索质量**：三路融合的名次只度量"多路共识"，不度量"查询和这行字到底多相关"。
  BM25 冠军经常是词面巧合（问"人事变动"，命中"交通运输局人事任免"的标题行）。
- **可用性**：新公告到达时，人工跑 collect→extract→validate→graph→scorer 五步；
  一篇坏文件让整批炸掉；全量重跑浪费；没有统一入口。

## 8.1 精排：cross-encoder 是什么、为什么放在融合之后

**bi-encoder（向量路）**：查询和文档**各自**编码成向量，靠余弦距离近似相关度。
优点是文档向量可以离线算好缓存；缺点是两个文本从没"见过面"，只能估距离。
用 SQL 的话说：像两表各自建好索引再估算 join，快但糙。

**cross-encoder（精排）**：把 `查询 + 文档` 拼在一起送进模型，**现场**输出一个
相关度分。两个文本逐 token 互相看见，精度天花板高得多；但每对都要跑一次模型，
不可能对全语料做——所以只配用在**小候选池**上。

于是分工定型（也是业界标准两段式）：

```
三路召回（宽，top-10）→ 加权 RRF 融合（宽池 top-20）→ cross-encoder 精排 → top-8
```

两个设计约束值得记住：

1. **精排只能重排池内候选**。RRF 第 21 名之后的东西，精排永远救不回来——
   召回和精排各司其职，谁也别越界。
2. **失败软降级**：精排服务挂了不炸检索，`degraded` 记一笔，退回 RRF 名次
   （`rerank.py` + `rag.py:search` 的 try/except，与三路召回同一套哲学）。

实现（`src/risklist_kg_miner/rerank.py`）：百炼 `gte-rerank-v2`。rerank 没有
OpenAI 兼容接口，用 stdlib `urllib` 裸调，零新依赖；离线兜底 `NoopRerank`
全 0 分返回，稳定排序下等价于"不精排"。

## 8.2 实测：预期修 precision，实测修的是排序

11 个标注查询、40 行语料，实测（`uv run --env-file .env python -m risklist_kg_miner evaluate`）：

| 配置 | recall@8 | precision@8 | MRR |
|---|---|---|---|
| 三路 · 百炼真嵌入+图谱（v0.7 最强） | 100% | 17% | 0.932 |
| 三路 · 真嵌入+图谱+**精排** | 100% | **17%** | **1.000** |

三个读数，一个比一个有讲头：

1. **MRR 0.932 → 1.000**：11 个查询的首条证据行**全部**被精排顶到第 1 位。
   单看"卫健委的人事变动"：BM25 的前两名是"交通运输局人事任免"标题行（词面
   命中"人事"），精排后这两行跌到 top-8 末尾（0.094），真正的证据行
   "免去 孙丽华 的 市卫生健康委员会副调研员"升到第 1（0.354）——查询里的缩写
   "卫健委"和文档里的"卫生健康委员会"，cross-encoder 在逐对打分时认得出。
2. **precision@8 没动（17%）**——v0.7 我们预期精排修这个数字，实测没修动。
   原因是**语料密度**：平均每个查询只有 ~1.4 条相关行，8 个槽位**必然**装
   5~6 个噪声，排序再完美 precision@8 也上不去。这不是精排没用，是分母的
   结构问题：precision@k 的可提升空间 = (相关行数 − 已进 top-k 的相关行数)
   与池内更好的候选数，两个都接近 0。
3. **recall@8 保持 100%**：精排没有把已在 top-8 的相关行挤出去——
   "换序不丢证"，这是精排不带副作用的安全证据。

> 面试要点：指标要对着语料密度读。同一套系统，换一个每查询 10 条相关行的
> 语料，precision@8 的精排增益立刻显形。我们在 40 行语料上能证明的是
> 排序上限（MRR=1.000），precision 的增益留给语料规模化之后。

## 8.3 流水线：增量更新怎么做才不漏检

`src/risklist_kg_miner/pipeline.py` 串起全链路，三个工程决策：

**① 增量的粒度是公告，但历史从图谱读回。** 图内已有 `:Notice` 的公告跳过
抽取（`Neo4jStore.notice_sources()`）；但合并不能只看本次新公告——新公告
"免去罗建军"必须和历史"任命罗建军"（notice-002）对上才算冲突。做法：
`Neo4jStore.load_records()` 把 `:Event` 流水（不可变留痕）读回成记录，
参与本次合并。**图谱在这里是历史事实源，不只是查询加速器**——v0.4 双写
建模（事件流水 + 当前状态）在这个场景兑现：流水可回放，所以增量不必
重新解析旧文件。`--force` 则全量重跑、不掺历史（重建语义）。

**② 失败隔离。** 单篇公告解析失败（编码损坏、版式突变）记入
`report.failures` 继续跑完整批。批处理的底线：一篇坏文件不毁一晚的采集。

**③ 软降级贯穿。** Neo4j 挂了 → 图谱步骤跳过、合并只覆盖本次公告（degraded
记明"历史冲突可能漏检"）；LLM key 没配 → 保守合并直接转人工复核。
系统在任何依赖残缺时都给出"当前能给出的最好结果 + 明说哪里缺"。

**为什么不做 LLM 裁决缓存**（面试常追问）：按 (人,职务,来源指纹) 缓存裁决
结论能省重复调用，但"新证据到来缓存必须失效"的指纹设计没想清楚之前，
宁可每次重裁决（冲突组很少，费用可忽略）。这和全项目"无跨会话记忆"的
架构承诺一致——复核结论回流才是设计里唯一的记忆扩展位（见教程六）。

## 8.4 CLI：四个命令收拢全链路

```bash
uv run python -m risklist_kg_miner ingest            # 一键流水线（增量）
uv run python -m risklist_kg_miner search "查询词"    # 三路召回 + 精排
uv run python -m risklist_kg_miner evaluate          # 评测消融
uv run python -m risklist_kg_miner review            # 风险分级 + 复核队列
```

（也注册了 console script：`uv run risklist-kg-miner ingest` 等价。）

增量实测（图里已有 6 篇时再跑）：

```
处理 0 篇: 无
增量跳过 6 篇（图内已有）: notice-001、…、notice-006
人工复核队列 0 条: 空
```

`--force` 全量重跑：抽取 14 条 → 合并 11 组（冲突 1）→ 落库成功 → 队列 1 条。
不配任何 key 时全程离线可跑（哈希向量 + noop 精排 + 保守合并），配 key 后
自动升级（真嵌入 + gte-rerank + DeepSeek 裁决）。

## 8.5 诚实边界

- 精排有真实延迟与费用：每查询一次 rerank 调用（20 对文档）。top-8 槽位少的
  场景（聊天引用 2~3 条证据）可以直接精排后取 top-3，进一步压噪声。
- 增量是**公告粒度**：公告内容变更（同名文件被改）不会触发重抽取，需要文件
  哈希指纹（列 v0.9+ 候选）。
- 评测语料冻结在标注集的 6 篇上（`evals.load_corpus` 固定枚举）；检索语料
  跟随目录（`rag._load_corpus` glob 全收）。**扩语料必须同步扩标注**，
  否则评测失真——这是 v0.7 方法学在 v0.8 的新推论。

## 面试话术

- "为什么 rerank 放在融合之后而不是替换融合？"——精排是逐对精算，代价随
  候选数线性涨；三路宽召回 + RRF 共识筛出 top-20 小池子再精算，是精度/成本
  的分界点。精排救不了池外漏检，所以召回层该宽还是宽。
- "rerank 带来多少提升？"——MRR 0.932→1.000（11 查询首条证据全排第 1），
  recall 不掉；precision@8 没动，因为 40 行语料每查询仅 ~1.4 条相关行，
  8 槽必装噪声——这是语料密度对指标的结构性约束，不是精排失效。
- "增量更新怎么设计？"——公告粒度跳过已入库来源；历史从 :Event 流水读回
  参与合并，跨公告冲突不漏检；不可变事件流水是增量的基石（v0.4 双写
  建模的兑现）。单篇失败隔离，依赖残缺软降级。
